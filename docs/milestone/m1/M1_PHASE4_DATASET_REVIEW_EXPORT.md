## 3. Scope, interfaces and invariants

**Scope:** read-only Workspace data filters and selected-record JSON/details; distinct Processing details and Explainability evidence inspection; grading and lesion readiness kept separate; reviewed-negative distinct from not-reviewed; CSV/JSON snapshot with schema/taxonomy/policy/revision identity, source hashes and patient grouping; DB/UI/export consistency; longitudinal pair visibility where authorized. Explanation evidence may be retained in an AI-evidence layer but never promoted to physician lesion labels by default. Do not ingest new research notebooks into clinical labels.

**Non-goals:** automatic train/validation/test split, training/fine-tuning, declaring absent lesions from empty boxes, promoting raw AI or model attention to human truth, exposing patient-level content in package docs, changing prior export interpretation without versioning, automatic referral/DME/longitudinal clinical judgment.

**Consumes:** scoped PostgreSQL source/review/annotation/audit state, truthful source-origin/permission lineage approved for its intended use (B01), three milestone fields and active annotation hash, Phase 2 approved group rubric if present, Phase 3 optional typed raw predictions/processing provenance. Current Bridge/dataset `source_type` evidence limited to `PUBLIC`/`SYNTHETIC` cannot itself authorize hospital export; pseudonymized hospital data are not public by default. **Produces:** read-only paginated/filtered **workspace-level** data, selected-record Processing details/JSON plus a distinct Explainability evidence view over the case-level evidence produced in P2-3/4 and P3-4, separate DR/lesion eligibility reasons, and versioned reproducible CSV/JSON/manifest snapshots with data-revision/checksum identity. “Read-only” means clinical source/review/annotation rows are not changed by inspection/export; an approved append-only export receipt/file/metadata record may be created outside those clinical rows. Storage location/permission of that receipt is a P4-3/4 reviewed design choice (`PENDING_OWNER` if hospital policy constrains it). Export may carry raw AI in a separately identified evidence layer but not in default gold labels.

**Invariant:** `dr_grade_training_ready` needs an eligible source, confirmed image, final physician grade/reviewer/time and valid `AI_ACCEPTED`, `AI_CORRECTED` or `MANUAL` grade provenance. `lesion_training_ready` needs an eligible source/confirmed image and current case-level annotation confirmation/hash/reviewer/time; grade is not required. Case-level confirmation does not individually confirm an AI ROI, and an empty active set can be confirmed reviewed without proving absence. Untouched AI and removed suggestions are not human labels; corrected ROI has `annotation_source=HUMAN_CORRECTION`, source detection lineage, original score/geometry separately and empty corrected score. Keep legacy compatibility fields but prefer task-specific readiness. Geometry is `original_image_pixels`. Master §23 controls any additive completeness semantics.

## 5. Acceptance and proof

For one frozen integrated **code** revision and a documented **short-lived consistent data read** (or explicit revalidation/retry) plus durable manifest/row-revision/count/hash receipt, a reviewer filters Workspace data, opens selected record and Processing details, sees human/AI distinctions and unknowns, exports CSV/JSON/manifest, and matches rows, counts, hashes and eligibility reasons to PostgreSQL at the same data state. Test restart and workspace isolation. Produce paired cases covering physician-confirmed grade only, lesion only, both, no review, case-level empty set, explicitly approved reviewed-none, untouched/removed AI, corrected AI, Ungradable/Unknown, source uncertainty and changed annotation hash. Defaults exclude unreviewed AI and model attention/explanation artifacts from gold. Confirm patient grouping only for a confirmed pseudonymous key; do not infer train/test split.

**E02 implementation note:** PostgreSQL `READ COMMITTED` can show different committed states to successive queries, and a `pg_export_snapshot` token is importable only while the exporting transaction remains open ([isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [snapshot synchronization](https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-SNAPSHOT-SYNCHRONIZATION)). The token is an execution-time coordination handle, **not** the durable dataset identifier. Select and test a bounded consistency/revalidation mechanism at implementation time; persist artifact identity through manifest metadata, row revisions, counts and checksums. Do not introduce a global revision/history framework or keep transactions open across clinician browsing just for this requirement.

Existing test locators: `tests/test_dataset.py`, `test_workflow.py`, `test_workspaces.py`, `test_resolver.py`; frontend Dataset/Workspace tests under `frontend/src`, exact test files to check at implementation baseline. **PROPOSED tests:** PostgreSQL repeatable snapshot under concurrent revision; DB/UI/export equality; reviewed-negative versus not-reviewed policy matrix; raw-AI contamination and pseudonym/privacy minimization; schema version round-trip. After implementation use `python -m pytest -q`, `python -m ruff check dr_support tests`, and from `frontend/` `npm test`, `npm run typecheck`, `npm run build`. No application test or export was run while drafting this plan.

## 6. Failure, dependencies, decisions and review gate

If a review revision changes during export, either read one consistent snapshot with recorded revision or fail and retry; never blend records from multiple states without disclosure. If policy/taxonomy version is unknown, mark eligibility unavailable and keep source/review data; do not guess a negative. If file hash/count mismatch, reject the export, preserve previous snapshot and log a redacted failure. Export is read-only **with respect to clinical/source review rows**; an approved append-only export receipt/files may be created under a documented access/retention policy. Restore/rollback follows Phase 1 authoritative database procedure, not editing CSV as truth.
