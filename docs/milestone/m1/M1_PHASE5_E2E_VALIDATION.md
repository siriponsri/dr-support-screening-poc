## 1. Purpose, authority and entry

Validate the actual integrated M1 build, not a separate demonstration implementation, against the Master §10 Phase 5 scenario and §§20, 23 definition/gates. The product remains the **M1 AI-assisted physician Labeling System**, not the M2 Clinical Screening System or autonomous diagnosis/referral product. Product, persistence, model runtime, clinical validation, export and operational readiness receive **separate** outcomes. A passing engineering E2E does not authorize production deployment or make CFP PRISM UWF-validated. See [Master](M1_MASTER_PLAN.md) and the Phase 1–4 specifications for shared contracts; this document is a candidate acceptance procedure awaiting owner review.

**Entry:** identify exact integrated commit, clean worktree, served frontend revision, schema/policy/taxonomy IDs, P1 migration/restore receipts, Phase 2 **selected** processing version and reviewed coordinate oracle/manual completeness contract, Phase 3 per-capability status and artifact digests where enabled, and Phase 4 export data-snapshot policy. Obtain authorized synthetic/deidentified engineering fixtures and separately approved clinical-owner review data/protocol. Models may remain explicitly disabled if scope/owner accepts a manual review product, but a claim of model capability requires that capability's qualification gate.

## 2. Baseline and contracts consumed/produced

## 3. Integrated scenario and invariants

Execute Master §10 scenario end to end on one integrated build:

1. Human selects approved top-level source in a Workspace; record source hash, **origin/permission independent of modality**, pseudonymous patient/eye/visit evidence, ambiguous/missing context and image confirmation. Public/synthetic engineering fixtures may proceed; any hospital fixture/path requires approved data-steward contract and restricted handling. Never label hospital input `PUBLIC`/`SYNTHETIC` simply because deidentified. No auto-scanning hospital storage. Verify source byte integrity and origin lineage at start and finish.
2. View **Original, Masked Analysis, AI Overlay and Explainability** for the selected Phase 2/3 processing contract/version; inspect transform/mask chain and verify that the displayed masked image is the representation bound to the model invocation. Exercise the selected path's success/failure/fallback and original-coordinate round trip against its pre-reviewed fixture oracle. If `border_component_v1` or v4 is not selected, its old success/failure is a historical compatibility comparison only, not a required production path. No mask state implies clinical gradability.
3. **Only for an enabled capability**, first record artifact origin/trust, byte result, selected runtime/build and actual loader security applicability/approval **before deserialization** (P3-1/3), then display bundle/checkpoint/domain and supported modality, deterministic selection and CFP/UWF warning, and exercise applicable success/unsupported/missing-checkpoint/timeout/OOM/restart cases against a pre-frozen qualification profile. If NB01 Explainability is enabled, verify its attention grid is bound to the same source/analysis/model invocation and is visibly labeled as model attention rather than lesion localization. For disabled models, test explicit disabled/unavailable UI and manual continuation; do not claim the model cases PASS from `N/A`. Manual grade/findings must continue, with no synthetic grade 0 or fake empty result.
4. Physician confirms image and grade separately, accepts/corrects/rejects/adds Core findings, optionally Advanced, and deliberately records approved completeness. Verify untouched AI remains evidence, corrected ROI lineage/score handling, confirmed-set hash invalidation, reviewed-none distinct from not-reviewed and no unapproved DME/referral rule.
5. Save to PostgreSQL, restart both services, reopen in same Workspace and test isolation from another Workspace. Compare revisions, audit, model/mask/provenance, preserved original, conflict behavior and recovery from unavailable Model API; repeat after approved backup/restore smoke on designated database.
6. Inspect Workspace data and Processing details and export eligible grade and lesion snapshots. For a data-steward-approved hospital path only, trace truthful origin and permission intake → Bridge request/response → P1 persistence → P4 manifest; verify rejection/unknown origin never becomes `PUBLIC`/`SYNTHETIC` or authorized export by default. Match DB/API/UI/export fields and hashes on one recorded **DB data snapshot/revision token** (or explicit changed-data revalidation), separate from the source-code commit; assert raw/unreviewed/rejected AI excluded from gold, independent task readiness, patient grouping only from confirmed pseudonymous key and no automatic split.
7. If owner permits same-eye side-by-side with date unknown, label order `UNKNOWN` and do not show before/after or change. Chronological comparison requires supported acquisition order, not ordinal. Learned change requires a separate Phase 3T model/clinical gate; otherwise show disabled. Test only approved applicable levels.

Stable **non-sensitive synthetic fixture/test IDs may be recorded** with expected results and revisions for reproducibility. Keep patient identifiers/codes, real-image source mapping and patient-sensitive content in authorized restricted locations outside repo/reconciliation reports; pseudonyms are not automatically publishable. Use approved access and redacted aggregate evidence for owner review. The UI must make model limitation and AI/human provenance visible beyond color alone; preserve `DESIGN.md` and existing frozen workflow behavior.

### Applicability and acceptance-profile record

Before the final run, REVIEW records a matrix for each check: selected processing version, enabled capability, fixture/oracle revision, acceptance-profile revision, applicability (`REQUIRED`/`N/A`), N/A reason/approver and result (`PASS`/`FAIL`/`NOT_RUN`/`N/A`). N/A is not PASS; NOT_RUN on a required check blocks that category. Exploratory L4 measurements may inform a proposed profile; owner approves/fixes the thresholds **before** the final qualification run. Any changed tolerance/threshold yields a new profile and run. Legacy helper tests remain optional historical comparison when the selected path excludes them. Do not infer a clinical pass from this matrix.

**Pass boundaries:** product/manual flow may pass while a model is disabled with honest UI and agreed scope. M1 completion proves the labeling/data lifecycle, not M2 screening/referral performance. ## 6. Failure, dependencies, decisions and gate

For a failed category, preserve logs/receipts without patient payload, stop the affected release claim and record reproducible defect, owner and remediation. Restore previous qualified app/model version using documented rollback, not a silent model or threshold swap; preserve immutable source and historical review revisions. A failed model is isolated and manual work remains possible; a failed database integrity/isolation gate blocks integrated product acceptance. An export hash/policy mismatch invalidates that snapshot until corrected. Do not proceed to hospital data or production while access, rights or clinical approval remains absent.

| Decision or dependency | Blocked outcome / independent work | Closure |
|---|---|---|
| Phase 1 P1-A/B/I and restore pending | Persistence/integrated E2E; isolated fixture tests can proceed | Integrated commit and designated PG/migration/restore receipts. |
| Phase 2 clinical completeness/taxonomy and processing comparison pending | Full clinical labeling and group-negative export/coordinate claim; manual core scenario can be exercised within current contract | Clinical owner rubric and P2/P3 measured transform evidence. |
| Grading external checkpoint and USPEC rights; PRISM CFP UWF limit | 3G runtime/production use and PRISM UWF clinical claim; honest disabled/manual product can proceed | Byte/load receipt, rights proof, clinical protocol/results and owner decision. |
| Dependency/L4/offline measurements absent | Model/operational readiness; other engineering checks proceed | Target measurements and owner-approved limits. |
| Approved UAT data access/clinical reviewer absent | Clinical-owner acceptance, not synthetic engineering E2E | Data steward and clinical-owner authorization/review. |

**Review gate:** submit category-specific receipts and explicit accepted limitations to owner/auditor. Owner chooses `READY_FOR_REVIEW`, `BLOCKED` or `DONE` for product as defined in Master; no `DONE` based on this candidate text or inherited historical tests. Separate independent clinical validation, rights and production authorization remain required as applicable.
